For a metrics dashboard that only requires server-to-browser updates, **Server-Sent Events (SSE)** is usually the simpler choice. SSE uses a standard long-lived HTTP connection, with the server sending a stream of text events that the browser consumes through `EventSource`. Browsers provide automatic reconnection, event IDs, and a straightforward programming model. It also fits naturally with existing HTTP authentication, proxies, and observability infrastructure.

The main limitations of SSE are that it is unidirectional, text-oriented, and dependent on keeping an HTTP response open. Some proxies and load balancers require timeout and buffering configuration, and connection limits can matter for older HTTP/1.1 clients. Binary data or highly customized protocols may also be awkward. With HTTP/2, many of the historical per-origin connection concerns are reduced.

**WebSockets** provide a persistent, full-duplex connection. They are more flexible: either side can send messages at any time, binary payloads are supported, and they can offer lower overhead for very high-frequency or interactive traffic. However, that flexibility adds complexity. Applications typically need to implement reconnection, heartbeat, connection state, message routing, and sometimes authentication refresh themselves. Infrastructure must also correctly support WebSocket upgrades and long-lived connections.

For a metrics dashboard, SSE is generally preferable when updates are moderate in frequency, payloads are naturally JSON or text, and the browser does not need to send messages over the same channel. Choose WebSockets if the dashboard will evolve into a highly interactive real-time application, requires client-to-server control messages, needs binary or custom framing, or operates at a scale where SSE’s HTTP behavior becomes a bottleneck.
